## Context

§2.6 of [version_2_Julia/docs/julia_fsa_writeup.pdf](version_2_Julia/docs/julia_fsa_writeup.pdf) describes a trivial-cost end-to-end test that strips out all the Stuart–Landau and F-coupling nonlinearities of the original FSA cost. The replacement cost is

> J(Φ) = −∫₀ᵀ B(t) dt,   λ_F = 0   (no fatigue penalty)

Under the FSA SDE, dB/dt = κ_B · a_B(A) · Φ − B/τ_B is monotone in Φ. The optimum is to pin Φ = Φ_max = 3 for every bin, driving B toward its highest equilibrium κ_B · Φ_max · τ_B.

The writeup states: *"The cost kernel is parametrised with state-integrand weights (w_B, w_F, w_A) (default (0,0,1), i.e. Eq 37). Setting (1,0,0) and λ_F = 0 gives the trivial cost. Driver: `version_2_Julia/tools/test_max_B_only.jl`."* The driver does not exist in the working tree, and the Phase-1 git-history sweep confirmed it has never existed in git history either — so this is a fresh recreation, not a recovery.

The expected result from §2.6 (light config):

- Posterior-mean θ̄ ≈ (+1.57, +2.12, +1.92, +1.77, +1.71, +1.52, +1.04, +0.42)
- Decoded schedule: day 0–8 Φ ∈ [2.68, 2.92] (essentially pinned to Φ_max), day 10–14 Φ tapers to 1.79
- Φ_mean = 2.73 vs Φ_max = 3.0
- Six tempering levels, auto-calibrated β_max = 12.5, ~55 s wall.

The point of the test: if the rebuilt driver reproduces those numbers AND the auto-generated traces show B saturating high while baseline-Φ=1 B sits low, then §2.6's conclusion stands — the FSA SDE integration, the RBF decoder, the GPU-kernel cost-accumulation pathway, and the framework parallel-chains HMC are all correct end-to-end. Any controller bug must therefore be confined to the A-cost surface specifically.

## User constraints

- **Only the new driver file may be added.** [version_2_Julia/models/fsa_high_res/gpu_control.jl](version_2_Julia/models/fsa_high_res/gpu_control.jl), [version_2_Julia/tools/plot_state_traces.jl](version_2_Julia/tools/plot_state_traces.jl), and every other existing file stay untouched.
- **The plot is generated by `plot_state_traces.jl`**, auto-invoked from the driver — same pattern as [version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl:609-636](version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl#L609-L636).
- The driver may be monolithic. That is fine.
- **Planning horizon is FIXED at 14 days** (per §2.11 of the writeup, page 10). The controller's planning horizon `H_plan = 14 d` (one chronic-B time constant `τ_B`) is held fixed regardless of bench duration — it is NOT `T_bench − t_elapsed`. The original Julia bench had this shrinking-horizon bug (`ctrl_n_steps` derived from `T_bench - mpc_plant.t_bin`); the partial fix at [version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl:489-491](version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl#L489-L491) now hard-codes `ctrl_n_steps = round(args["T-days"] / DT_DAYS)`. The new driver must honour the same convention: planning is always over 14 d, even if the user later extends the plant rollout.

The existing `fsa_cost_kernel!` in `gpu_control.jl` is hard-coded to Eq 37 (line 144: `cost_per_thread[i] = Float64(fma(lam_F, bar_acc, -A_acc))`). It does not expose `(w_B, w_F, w_A)`. Because we cannot modify it, the new driver inlines its own copy of the kernel + target + log-density closure with the weights added.

## Approach

The new file [version_2_Julia/tools/test_max_B_only.jl](version_2_Julia/tools/test_max_B_only.jl) is one self-contained Julia driver. External dependencies:

- `CUDA`, `KernelAbstractions`, `Random`, `Statistics`, `Printf`, `JLD2`, `JSON3`, `Dates`
- The FSA model package (for `TRUTH_PARAMS`, `INIT_STATE`, `A_TYP`, `F_TYP`, `BINS_PER_DAY`, `StepwisePlant`, `advance_subdaily!`)
- The framework: `SMC2FC.run_tempered_smc_gpu`

It does **not** import `GPUControl` — it carries its own kernel and target.

1. **CLI parsing** — dict-based, copying [version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl:16-55](version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl#L16-L55). `FSA_STEP_MINUTES` set BEFORE the model import (mandatory — module reads it at load time). Knobs:
   - `--T-bench-days` (default 14) — how long the **plant** rolls forward (sets the visible time-axis on the trace plot).
   - `--H-plan-days` (default 14, FIXED per §2.11) — the **controller's** planning horizon. Default value comes from §2.11: one chronic-B time constant `τ_B = 14 d`. Exposed as a flag for diagnostic experimentation only.
   - `--step-minutes` (default 15)
   - `--n-smc` (default 64)
   - `--n-inner` (default 16)
   - `--num-mcmc` (default 3)
   - `--hmc-leap` (default 8)
   - `--hmc-step` (default 0.2)
   - `--max-levels` (default 15)
   - `--target-nats` (default 8.0)
   - `--w-B` `--w-F` `--w-A` (defaults 1.0 / 0.0 / 0.0)
   - `--lam-F` (default 0.0)
   - `--seed` (default 42)
   - `--output-dir` (default `outputs/fsa_high_res/test_max_B_only/run_<timestamp>`)

   Defaults reproduce the light §2.6 config (T_bench = H_plan = 14 d). The split between `T_bench` and `H_plan` is the §2.11 distinction made concrete — the planning horizon does not shrink with elapsed time and does not have to equal the bench duration.

   **Validation:** at startup, error out if `T_bench > H_plan`. The driver runs a single open-loop plan and applies it directly to the plant; if the plant outlives the plan, there is no behaviour we can defensibly fall back on (that would require closed-loop replanning, which is out of scope for this trivial-cost test). Erroring is safer than silently extending Φ=1 past the plan end.

3. **Local kernel `fsa_cost_kernel_weighted!`** — verbatim copy of [version_2_Julia/models/fsa_high_res/gpu_control.jl:48-146](version_2_Julia/models/fsa_high_res/gpu_control.jl#L48-L146) with the following surgical changes:

   - Add `B_acc, B_comp` and `F_acc, F_comp` Kahan-compensated accumulators alongside the existing `A_acc, A_comp` and `bar_acc, bar_comp`. They use the same compensated-summation block as the original `A_acc` lines (gpu_control.jl:91–95).
   - Add three kernel-args `w_B, w_F, w_A` (Float32 scalars).
   - Replace the cost line
     ```julia
     cost_per_thread[i] = Float64(fma(lam_F, bar_acc, -A_acc))
     ```
     with
     ```julia
     state_int = fma(w_A, A_acc, fma(w_F, F_acc, w_B * B_acc))
     cost_per_thread[i] = Float64(fma(lam_F, bar_acc, -state_int))
     ```

   At default weights (1, 0, 0) and λ_F = 0 this collapses to `-B_acc`, exactly the §2.6 trivial cost. At (0, 0, 1) and λ_F = 1 it reproduces Eq 37 byte-for-byte (modulo harmless extra `B_acc` / `F_acc` adds), which is a useful sanity-equivalence check.

   Everything else — Horner-form μ, FMA drift, state-dep diffusion, boundary reflection, fp32 inner / fp64 cost-output convention, all the §2.8 algebraic-stable rearrangement constants — stays bit-identical to `gpu_control.jl`.

4. **Local target struct `FSAWeightedGPUTarget`** — verbatim copy of [version_2_Julia/models/fsa_high_res/gpu_control.jl:151-179](version_2_Julia/models/fsa_high_res/gpu_control.jl#L151-L179) with three extra `Float32` fields `w_B, w_F, w_A`. Adds keyword args `w_B::Real = 1.0, w_F::Real = 0.0, w_A::Real = 0.0`.

5. **Local `gpu_cost_log_density_batched_weighted` + `make_log_density_fn_weighted`** — same calling shape as the originals ([version_2_Julia/models/fsa_high_res/gpu_control.jl:252-312](version_2_Julia/models/fsa_high_res/gpu_control.jl#L252-L312)), just plumbing the extra `target.w_B, target.w_F, target.w_A` through to the kernel launch. Returns per-chain MC-averaged `−J`.

6. **RBF decoder helper** `decode_per_bin_phi(...)` — exact copy of [version_2_Julia/tools/test_one_plan_fp64.jl:47-63](version_2_Julia/tools/test_one_plan_fp64.jl#L47-L63). RAW (not row-normalised) Gaussian basis, matching the kernel.

7. **SMC² planning call**
   - **Planning horizon (§2.11):** the SMC² target uses `n_steps = H_PLAN_DAYS * BINS_PER_DAY` — i.e. always 14 d at default. The controller never sees `T_BENCH` and never sees a shrinking horizon.
   - Build target with weights from CLI (defaults (1,0,0), λ_F=0), `init_state = [0.05, 0.30, 0.10]`, `params = TRUTH_PARAMS`, `noise_seed = seed`.
   - `M_MAX = N_SMC * (1 + 2 * D)` where `D = 8`.
   - Time + run:
     ```julia
     t0 = time()
     posterior, n_temp, β_max = run_tempered_smc_gpu(
         log_density_fn, M_MAX, N_SMC, D,
         0.0, SIGMA_PRIOR, MersenneTwister(seed);
         target_nats = TARGET_NATS, target_ess_frac = 0.5,
         max_lambda_inc = 0.20, max_temp_levels = MAX_LEVELS,
         num_mcmc_steps = NUM_MCMC, hmc_step_size = HMC_STEP,
         hmc_num_leapfrog = HMC_LEAP,
         chees_L_candidates = [16, 32, 64, 128, 256],
         h_fd = 1e-4, calib_n = 64, verbose = true,
     )
     wall = time() - t0
     ```
   - Decode θ̄ → `phi_per_bin` (length `N_STEPS = T_days * BINS_PER_DAY`).

8. **Plant rollout (MPC + baseline)** — feeds `plot_state_traces.jl`'s expected JLD2 schema.

   `StepwisePlant` API confirmed in [version_2_Julia/models/fsa_high_res/_plant.jl:339-403](version_2_Julia/models/fsa_high_res/_plant.jl#L339-L403): `advance_subdaily!(plant, Phi_subdaily)` takes a per-bin Φ vector of length `stride_bins` and pushes the full trajectory + obs into `plant.history`.

   Driver does:
   ```julia
   STRIDE_BINS = BINS_PER_DAY                    # one stride per day
   N_STRIDES   = T_BENCH_DAYS                    # T_bench, NOT H_plan
   # phi_per_bin has length H_PLAN_DAYS * BINS_PER_DAY (§2.11).
   # T_BENCH_DAYS ≤ H_PLAN_DAYS is enforced at CLI parse time, so the
   # slice phi_per_bin[1 : N_STRIDES * STRIDE_BINS] is always well-defined.
   truth_dict  = Dict{Symbol,Float64}( ... TRUTH_PARAMS as a Dict ... )

   mpc_plant  = StepwisePlant(truth_params=truth_dict,
                              init_state=(B=0.05, F=0.30, A=0.10),
                              dt=DT, seed_offset=seed)
   base_plant = StepwisePlant(truth_params=truth_dict,
                              init_state=(B=0.05, F=0.30, A=0.10),
                              dt=DT, seed_offset=seed + 1000)

   daily_phi_per_stride = Float32[]
   for d in 0:N_STRIDES-1
       slice = phi_per_bin[d*STRIDE_BINS+1 : (d+1)*STRIDE_BINS]
       advance_subdaily!(mpc_plant, Float32.(slice))
       push!(daily_phi_per_stride, Float32(mean(slice)))
       advance_subdaily!(base_plant, fill(Float32(1.0), STRIDE_BINS))
   end

   traj_mpc  = vcat(mpc_plant.history[:trajectory]...)   # (T_BENCH_BINS, 3)
   traj_base = vcat(base_plant.history[:trajectory]...)
   ```

9. **JLD2 save + auto-plot** — same recipe as [version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl:587-636](version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl#L587-L636).

   ```julia
   data_path = joinpath(out_dir, "data.jld2")
   JLD2.jldopen(data_path, "w") do f
       f["trajectory_mpc"]       = Float32.(traj_mpc)
       f["trajectory_baseline"]  = Float32.(traj_base)
       f["daily_phi_per_stride"] = daily_phi_per_stride
       f["BINS_PER_DAY"]         = BINS_PER_DAY
       f["STRIDE_BINS"]          = STRIDE_BINS
       f["dt_days"]              = DT
       f["F_max"]                = 0.40
       f["theta_post_mean"]      = theta_post_mean
       f["phi_per_bin"]          = Float32.(phi_per_bin)
       f["n_temp"]               = n_temp
       f["beta_max"]             = β_max
       f["wall_seconds"]         = wall
       f["weights"]              = [w_B, w_F, w_A]
       f["lam_F"]                = lam_F
   end

   try
       let plotters_dir = @__DIR__
           include(joinpath(plotters_dir, "plot_state_traces.jl"))
           data_dict = Base.invokelatest(Main.load_run_data, data_path)
           traces_path = joinpath(out_dir, "test_max_B_only_T$(T_DAYS)d_traces.png")
           Base.invokelatest(Main.plot_state_traces, data_dict; out_path=traces_path)
           @info "wrote $traces_path"
       end
   catch e
       @warn "plot generation failed (data.jld2 still saved)" exception=(e, catch_backtrace())
   end
   ```

   The `include` + `Base.invokelatest` dance sidesteps the world-age issue documented in the bench at [version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl:618-621](version_2_Julia/tools/bench_smc_full_mpc_fsa_gpu.jl#L618-L621).

## Verification

End-to-end on the same machine the writeup was produced on:

1. **Default invocation reproduces §2.6 numbers** (light config, weights (1,0,0), λ_F = 0):
   ```bash
   cd version_2_Julia && julia --project=. tools/test_max_B_only.jl
   ```
   Acceptance:
   - all 8 components of θ̄ are positive,
   - Φ̄(day 0..8) ≥ 2.5 (essentially pinned to Φ_max = 3),
   - Φ̄(day 14) in roughly [1.5, 2.0] (Bayesian shrinkage near boundary anchor),
   - n_temp = 6 ± 2,
   - β_max in roughly [10, 16],
   - wall ≤ ~120 s on RTX 5090.
   - The auto-generated trace PNG exists at `outputs/.../test_max_B_only_T14d_traces.png` and shows MPC-driven B sitting visibly above baseline B for most of the horizon.

2. **Sanity-equivalence with Eq 37**: re-run with `--w-B 0 --w-F 0 --w-A 1 --lam-F 1.0` should produce a posterior-mean θ̄ qualitatively matching `test_one_plan_fp64.jl` at matching config (recovery → overload, Φ ramping low-to-high). Numerical bit-equivalence is not expected (different RNG draws and different FD perturbations through the SMC chain), but the schedule shape should match. Confirms the inlined kernel hasn't silently drifted from `fsa_cost_kernel!` at default weights.

3. **Heavy-config monotone optimum**: `--n-smc 1024 --n-inner 128` should still pin Φ to Φ_max in days 0–8 (the cost surface is monotone in Φ and has no fp32 cancellation hot-spots when w_A=0, w_F=0). This is the §2.6 conclusion: when the cost is unambiguous, the kernel + decoder + framework HMC chain works; if the heavy-config recovery → overload bench fails, the bug is in the A-cost surface specifically.

If verification step (1) fails, the most likely sources are (a) typo in the cost-line replacement that drops a sign or weight, (b) off-by-one in the per-day aggregation block, or (c) JLD2 schema key mismatch with the plotter. All three are localised to the new file.

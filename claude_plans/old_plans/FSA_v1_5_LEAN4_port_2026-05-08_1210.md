## Context

Two prior attempts at the FSA porting problem clarified what works and what doesn't:

1. **FSA-v5 Python ↔ LEAN4** (the lean4-first charter). The Lean4 side worked as a type-safety scaffold, but Python remained the production path and re-introduced the same pattern-matching bug class on every iteration.
2. **FSA-v5 Python → Julia** (`version_3_julia/`, commit `392d85b`, 30 files / 7,171 lines). The user reports it was "too much for a human to understand", "the controller does not optimize the growth of A", and that the bug class is the same imperative-Python-style "wooden" code the charter was supposed to escape.

The user has now authored a much smaller, **purely functional v1.5 Julia codebase** at `version_1_5_Julia/models/fsa_high_res/` (1,498 LOC across 7 files vs the v3_julia 7,171). v1.5 was deliberately written with `Match.jl` `@match … begin … end` at every site that needs pattern matching, because Lean4's `match … with` is structurally near-identical (writeup §7 "Lean4-port mapping appendix"). That alignment is the whole point: it makes the Julia ↔ Lean4 bridge **mechanical**.

Standing rule from the charter is unchanged — Lean4 is the formal source of truth — but the implementation pivot is:

- **Old**: Lean4 spec → Python implementation, diff-tested at the FFI boundary.
- **New**: Lean4 spec ↔ Julia implementation. Julia is the production path; `@match` sites in Julia map line-for-line to `match … with` in Lean4. **Lean4 is the larger, verifiable codebase; the Julia surface is a small mechanical port from it.**

For this first pass v1.5 Julia is already validated (FIM rank 7/7, κ=2.95×10⁷ on the realistic 14-day window; the 28-day open-loop bench reproduces v1's reference behaviour). So this work is **bootstrap**: translate the existing v1.5 Julia → Lean4, verify they agree via diff testing. From then on Lean4 leads and Julia is mechanically derived.

## Goal

A new directory `version_1_5_LEAN/` containing a Lean4 reference for FSA v1.5 — typed defs + runnable native binary — that:

1. Type-checks under `lake build`.
2. Mirrors the v1.5 Julia public API one-for-one.
3. Is wired to a Julia diff-test harness that round-trips every public function against the Lean4 binary at 1e-6 (single-step) / 1e-4 (integrated) tolerance.
4. Translates each Match.jl `@match` site to a Lean4 `match … with` site (the mechanical bridge).

## The three @match sites (the mechanical bridge)

These are the only `@match` sites in v1.5's *non-GPU* code. Each maps line-for-line to a Lean4 `match … with`. The sketches are already in writeup §7.1 — Lean4 transcription is a direct copy.

1. **`params_v15_to_v1_nt`** (`simulation.jl:110-143`) → `Fsa.V15.Adapters.params_v15_to_v1`. Lean4 inductive `ParamsForm` discriminates Dict vs NamedTuple input; Julia `@match p begin ::Dict => …; ::NamedTuple => … end` becomes `match p with | .dictForm d => … | .ntForm nt => …`.
2. **`_reflect_unit`** (`_plant.jl:57-61`) → `Fsa.V15.Plant.reflect_unit`. Julia `@match` on guarded predicates collapses cleanly to nested `if/else` in Lean4.
3. **`apply_prior`** (writeup §7.1) → `Fsa.V15.Estimation.apply_prior`. Inductive `PriorKind { logNormal, normal }`; clean `match k with …` dispatch.

The GPU-side @match sites (`gpu_pf.jl` segment-boundary guard, accept/reject atom, vector destructure) are explicitly **out of scope** per writeup §7.2 and stay Julia-side.

## Differential-test harness

Mirrors the proven pattern from `version_3_julia/test/test_lean_diff.jl` (which is already green at 1e-6):

1. **Lean4 `Main.lean`** is a `def main : IO Unit` that reads one JSON line per stdin describing one function call (function name + JSON-encoded args), evaluates the function, writes one JSON line on stdout. Functions covered: `drift`, `diffusion_state_dep`, `em_step_substepped`, `params_v15_to_v1`, `reflect_unit`, `plant_step`, `plant_rollout` (one stride), `obs_log_weight`, `apply_prior`.
2. **Julia `diff_test/test_lean_diff_v15.jl`** opens a bidirectional pipe to the compiled Lean4 binary (`open(`$LEAN_BIN`, "r+")` — the pattern that worked in v3_julia after the initial `pipeline()` attempt failed). Generates random inputs via `Random.MersenneTwister(42)` in the physiological-bound box (B,F,A ∈ [0,1]; params per `DEFAULT_PARAMS`'s order-of-magnitude ranges), sends one JSON line per case, parses the response, calls the equivalent Julia function, asserts `|Δ| < 1e-6` per scalar (single-step) or `1e-4` per scalar (integrated over `plant_rollout`).
3. The Julia driver runs under `Pkg.test()` after building the Lean4 binary with `lake build` in `version_1_5_LEAN/`. Manual run: `julia --project=. diff_test/test_lean_diff_v15.jl`.

Tolerance choice (matches charter §5.6): 1e-6 single-step / 1e-4 integrated.

## Effort estimate (AI-paced)

This is **mechanical translation**, not design work. The writeup §7 already provides side-by-side Julia↔Lean4 sketches for every `@match` site, and the existing `FSA_model_dev/lean/Fsa/V5/` codebase is the template for namespace, `structure … where … deriving Repr`, lakefile, toolchain, and Main.lean JSON-bridge style. ## Risks

- **RNG key derivation.** Julia `hash((key, :obs))` doesn't have a clean Lean4 equivalent. Resolution: in the diff test, pass *pre-drawn Gaussian noise tuples* to both implementations rather than RNG keys; the implementations themselves don't need to reproduce the hashing logic. Both stay deterministic and bit-identical for the same noise input.
- **Mathlib dep.** Pulling Mathlib is heavy (`lake exe cache get` first, then ~1-2 min link time). v1.5's math is small enough that we *could* skip Mathlib — `Float.exp / Float.log / Float.sqrt / Float.max` are in Lean4 core. But the `FSA_model_dev/lean/` project already uses Mathlib, and mirroring that convention is the safer default. Recommend **starting Mathlib-on**; revisit if compile time becomes painful.
- **Float precision.** Julia `Float64` ↔ Lean4 `Float` are both IEEE-754 double; bit-identical. Tolerance could be tightened to 1e-12 single-step; we keep 1e-6 to match charter convention and absorb any libm differences in `exp/log/sqrt`.
- **Bootstrap vs forward direction.** This port is *bootstrap* (Julia exists first → Lean4 derived). Going forward, Lean4 leads and Julia is mechanically derived. The plan doesn't gate on the forward-direction process; once the bootstrap diff-test is green, the standing rule from the charter kicks in.
- **`Adapters.params_v15_to_v1` Dict case.** Julia's `Dict{Symbol,Float}` doesn't have a clean Lean4 equivalent. The diff-test sends only the `ntForm` case from Julia (the production path). The `dictForm` case is preserved in Lean4 as a thin wrapper over `(Symbol → Float)` for symmetry but is not exercised at 1e-6 tolerance.

## Verification — how to know this is working

1. `cd version_1_5_LEAN && lake build` succeeds with 0 warnings.
2. Built binary at `build/bin/Main` (or `lake exe Main`) accepts the JSON-line protocol round-trip.
3. `cd version_1_5_Julia && julia --project=. diff_test/test_lean_diff_v15.jl` — every public function asserts green at 1e-6 (single-step) / 1e-4 (integrated `plant_rollout`).
4. Each of the three `@match` sites has at least 5 randomised diff cases per `Random.seed!(42)`.
5. If a diff case goes red: per the charter rule, the bug is by construction in the Julia. The failing input + both impls' outputs go into a `claude_plans/` follow-up note.

## Decision

Adopt this plan. The work is translation, not research. ~8 hours of human-equivalent effort. The Lean4 codebase becomes the larger, verifiable artefact; the v1.5 Julia surface is the small mechanical port that already exists and is already validated. Going forward, Lean4 leads.

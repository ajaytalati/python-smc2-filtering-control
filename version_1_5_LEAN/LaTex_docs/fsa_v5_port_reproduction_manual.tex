\begin{abstract}
This document is the operational companion to the
\emph{LEAN4-First Charter}, the \emph{FSA v5 Technical Guide}, and
the \emph{LaTeX $\to$ Lean4 $\to$ Julia pipeline} doc. Given two
on-disk inputs --- the FSA v5 technical guide
(\path{LaTex_docs/FSA_version_5_technical_guide.tex}) and the Lean4
source files at \path{Fsa/V5/} --- this manual walks a fresh human
or AI agent through the seven phases needed to produce a verified
closed-loop SMC$^2$-MPC bench. Each phase is a small set of files,
an imperative procedure, and a single-command verification gate.
The final gate is an end-to-end T=7 day bench that should complete
in $\sim 6$ minutes on RTX 5090 and produce
\path{data.jld2}, three diagnostic PNGs, and a recovered final
state matching the verified reference run on 2026-05-09.

The manual is deliberately operational (\emph{do X; verify Y; then
do Z}); the chronological narrative of how the port was
constructed is captured separately in
\path{models/fsa_v5/PORT_LOG.md}.
\end{abstract}

\subsection{One-sentence goal}

\textbf{Given the FSA v5 tech guide and the Lean4 source files in
\path{Fsa/V5/}, produce a verified Julia port that runs the
closed-loop SMC$^2$-MPC bench end-to-end.}

\subsection{Why this manual exists}

The work to date is captured only in conversational history and in a
chronological \path{PORT_LOG.md}. Neither is a stable artefact a
future reader can pick up and execute without reverse-engineering
the order of operations and the rationale at each step.

LLM coding agents are a lossy medium for code: the LEAN4-First
Charter exists precisely because pattern-matching agents introduce
transcription errors when porting math. The differential test
catches transcription errors at machine precision, but only if a
future port is structured so that the diff-test gates apply. This
manual prescribes the structure, the gates, and the per-phase pass
criteria so that the verifiability of the work is preserved.

The result of every closed-loop bench --- recovered $\theta$
posteriors, controller plans, $A$-accumulation traces --- is only
as trustworthy as the pipeline that produced it. The manual is
the pipeline's contract: \emph{if you follow these steps and hit
these gates, you have the same pipeline that produced the verified
reference run on 2026-05-09}.

\section{Phase 3 --- Differential test}
\label{sec:phase3}
% =============================================================================

\subsection{Background: what is a differential test, and why use one here?}
\label{sec:diff-test-explained}

A \textbf{differential test} is a test that checks two independent
implementations of the same mathematical function and asserts they
produce the same answer on every input. Think of it as
spell-checking a translation by feeding the same paragraph into two
dictionaries: if their definitions disagree on any word, you know
that word was mistranslated.

\paragraph{Why a differential test is the right tool here.} The work
in Phases 1 and 2 is, at its core, \emph{transcription}. The maths
already exists (in the FSA v5 technical guide and the Lean4 source);
the Julia code is supposed to encode the same arithmetic in a
different programming language. The bugs that show up in this kind
of work are typos, sign flips, swapped arguments, off-by-one
indexing --- not algorithmic errors. These bugs are very hard to
spot by reading the code, and very easy to expose by feeding the
same numerical input to both implementations and watching for a
disagreement on the output. A differential test does exactly that,
mechanically, on hundreds of inputs in a few seconds.

\paragraph{Who plays which role?} The Lean4 binary
\texttt{fsa\_v5\_cli} (Phase 1's deliverable) is the \emph{reference}.
It is small, type-checked, and was reviewed line-by-line against
the technical guide --- it is treated as the ground truth. The
Julia code from Phase 2 is the \emph{implementation under test};
the diff test asks ``does Julia produce the same number Lean did?''
and flags any disagreement.

\paragraph{How the two sides talk to each other.} Lean4 compiles
to a native binary that reads one JSON request per line on stdin
and writes one JSON response per line on stdout. The Julia test
driver:

\begin{enumerate}[itemsep=2pt]
  \item launches the binary as a long-lived subprocess (\emph{one}
        startup cost per test run, not per assertion);
  \item for each test case, builds a JSON object describing the
        function call (e.g.\ \texttt{\{"fn": "drift", "state": [...]
        , "phi": \{...\}, "params": \{...\}\}}), writes it on
        stdin, and reads the JSON response on stdout;
  \item runs the same call locally in Julia;
  \item asserts \texttt{|Julia $-$ Lean4| < tol} component-by-component
        (or \texttt{isapprox}-style for arrays).
\end{enumerate}

The subprocess + JSON-line protocol is just a robust way of
calling a function across a programming-language boundary
(Lean and Julia don't share a runtime). It is mechanically simple;
the same pattern works for any pair of compiled-to-native
languages.

\paragraph{The pre-drawn-noise trick (and why it matters).} Some
functions in the model involve random numbers --- in particular,
the Euler--Maruyama step in \texttt{em\_step\_v5} adds a Gaussian
noise increment to advance the SDE by one bin. If Julia and Lean
each drew their own noise from their respective random-number
generators, they would draw \emph{different} numbers (the two
languages have different RNGs and even different default seeds),
so the outputs would always differ --- not because the maths
disagrees but because the inputs were different. That is a false
fail.

The fix is the \textbf{pre-drawn noise} convention: the test
driver draws the noise vector \emph{once} on the Julia side, then
passes that exact noise array to \emph{both} the Julia call and
the Lean call. Both implementations now run their EM step on
\emph{identical} noise. Any output disagreement is purely due to
the deterministic arithmetic (sign error, wrong coefficient,
swapped state component, etc.) --- which is what we actually want
to detect.

\paragraph{Why a tolerance, not strict equality.} Floating-point
arithmetic is not exact. Two valid implementations of the same
formula can produce results that differ in the last few bits
because of how the rounding accumulates through the operations
(IEEE-754 round-off). Insisting on \texttt{==} would fail
correctly-written code. The diff test instead asks ``do the two
results agree to $n$ digits?''. The threshold is the
\textbf{tolerance}.

The manual uses two tolerances. The bulk of the tests use $10^{-6}$
(roughly six matching digits): tight enough to catch any real bug,
loose enough to absorb the round-off of single-arithmetic-operation
disagreement. The integrated EM step uses a looser $10^{-4}$
because it composes 4 substeps plus a Wiener increment, so
round-off accumulates more. The exact tolerance for each function
is in the table below; the rationale per row is the only piece a
fresh reader needs to internalise.

\paragraph{What ``green'' means.} A green test run means: every Julia
function in Phase 2, on every random input the test threw at it,
produced a number indistinguishable from Lean's at the prescribed
tolerance. The reverse is also true: \emph{any} red assertion
points at a specific function whose Julia code disagrees with the
Lean reference, and the assertion message tells you exactly which
input triggered the disagreement and by how much. That makes
debugging a port mechanical: you do not have to read the code; the
test tells you which line to fix.

\subsection{Implementation in this manual}

\paragraph{Goal.} Verify every Julia function from Phase 2 against

sends each function's inputs as JSON on stdin, reads the Lean4
result on stdout, runs the same call locally in Julia, and asserts
\texttt{|Julia $-$ Lean4| < tol}.

\section{Phase 4 --- GPU port (SOFT cost only)}
\label{sec:phase4}
% =============================================================================

\paragraph{Goal.} Produce two GPU files that run the v5 SDE math
on-device: \texttt{gpu\_pf\_v5.jl} (the inner-PF kernel for the
filter) and \texttt{gpu\_control\_v5.jl} (the cost kernel for the
controller). Each file mirrors its v1.5 counterpart's plumbing
verbatim and only swaps the math block.

\paragraph{Architectural rule (cite the LEAN4-First Charter).}

\begin{quote}
Copy v1.5's plumbing verbatim --- kernel structure, RNG-per-thread
layout, log-likelihood reduction, NaN guards, framework hooks. Only
swap the per-particle (or per-trial) math block with the v5
versions transcribed from the diff-tested CPU functions. Do NOT
rewrite the plumbing; that is the AI-fuckup-prone surface.
\end{quote}

\paragraph{Dimension bumps (the only changes inside the kernel
plumbing).}

\begin{itemize}[itemsep=2pt]
  \item Particle state dim: $3 \to 6$ (allocations, indexing, packing).
  \item Obs dim: $3 \to 5$ Gaussian + Bernoulli, with explicit
        per-bin gates as \texttt{Float32} masks (multiply each
        channel's log-likelihood by its gate).
  \item Params per chain: $14 \to 15$ estimated dynamics +
        $22$ estimated obs-channel + $14$ frozen.
  \item Boundary: reflect $\to$ clamp/floor (matches Phase 2).
\end{itemize}

\paragraph{SOFT cost only.} The v5 cost kernel implements

\[
J(\theta) = \lambda_\Phi \int_0^T (\Phi_B^2 + \Phi_S^2) \, dt
            \;-\; \int_0^T A \, dt
            \;+\; \lambda_F \int_0^T \max(F - F_{\max}, 0)^2 \, dt
            \;+\; \lambda_{\rm chance} \int_0^T \sigma\!\left(
              \beta \cdot \frac{A_{\rm thr} - A}{\rm scale}
            \right) dt.
\]

The chance surrogate uses a constant $A_{\rm thr}$ (default 0.05)
rather than the per-bin $A_{\rm sep}(\Phi_t)$ from
\texttt{find\_a\_sep}. The full per-bin form would require either
a CPU-side precompute or a separate GPU prep kernel
(${\sim} 286$M \texttt{mu\_bar} evaluations per call at production
sizes); deferred. The HARD chance-constraint variant (with
indicator instead of sigmoid) is deliberately out of scope.

\paragraph{Single-thread debug entry points.} Each kernel exposes a
1-thread debug function that the diff test invokes for
\texttt{ndrange = 1}:

\begin{itemize}[itemsep=0pt]
  \item \texttt{gpu\_propagate\_one!} runs the PF kernel for one
        \emph{(chain, particle, bin)} and returns the next 6D state
        and the accumulated log-weight.
  \item \texttt{gpu\_cost\_one!} runs the controller cost kernel for
        one \emph{(chain, trial)} and returns the scalar cost.
\end{itemize}

These let the diff test compare the GPU per-thread math against the
diff-tested CPU functions (\texttt{em\_step\_v5},
\texttt{obs\_log\_weight\_v5}, the inline cost replicate) at fp32
precision ($\sim 10^{-3}$ absolute). Closes the GPU-coverage gap
documented in the pipeline doc \S8.

\paragraph{HMC clarification --- both filter and controller HMC live
in the framework, not in the model.} The v5 model exposes two
closures:

\begin{itemize}[itemsep=0pt]
  \item \texttt{gpu\_log\_density\_v5(target, U, grid\_obs, key)} ---
        the filter's $\log p(y \mid \theta)$ closure.
  \item \texttt{make\_log\_density\_fn\_v5(ctrl\_target)} --- the
        controller's $-\mathrm{cost}(\theta)$ closure.
\end{itemize}

\texttt{SMC2FC\_functional} consumes these via
\texttt{parallel\_hmc\_one\_move\_generic!} +
\texttt{chees\_pick\_L\_generic} (filter) and
\texttt{run\_tempered\_smc\_gpu} (controller). \textbf{No new HMC
code is needed in the model directory.} The legacy
model-specific \texttt{parallel\_hmc\_one\_move} in v1.5's
\texttt{gpu\_pf.jl} is dead code.

\section{Troubleshooting and known gotchas}
\label{sec:trouble}
% =============================================================================

\paragraph{Lean's \texttt{Float.toString} floor at 6 significant
digits.} Manifests as \texttt{schedule\_from\_theta} test failures
at $10^{-6}$ atol when the output magnitude is $\sim 3$
($\Phi_{\max} \cdot \mathrm{sigmoid}$). Fix: use \texttt{rtol=1e-5}
for schedule outputs. Documented in \texttt{test\_lean\_diff\_v5.jl}.

\paragraph{GPU plumbing reuse.} Don't refactor the kernel /
framework glue when porting v5. Verbatim copy from v1.5 with
math-block swap is the rule. Refactoring there is the
AI-fuckup-prone surface.

\paragraph{fp32 inner loops, fp64 outer state.} Project convention
(see \texttt{CLAUDE.md} GPU-dtype section). Do not annotate
\texttt{Float64} inside SDE inner loops on the GPU; doing so
requests fp64 throughout and tanks RTX 5090 throughput by
$\sim 64\times$.

\paragraph{\texttt{FSA\_STEP\_MINUTES} env var must be set before
model import.} The bench driver sets
\texttt{ENV["FSA\_STEP\_MINUTES"] = ...} before
\texttt{include("FSAv5.jl")}. Reorder this and \texttt{BINS\_PER\_DAY}
resolves to the wrong value because \texttt{simulation\_v5.jl}
reads the env var at module-load time.

\paragraph{\texttt{FSA\_V5\_DRY\_RUN=1} for dry-run smoke testing.}
Loads the driver and all its includes but skips \texttt{main()}.
Useful for catching parse / unresolved-symbol errors without
running the bench.

\paragraph{\texttt{ot-max-weight = 0.0} default.} Setting this $> 0$
enables the framework's OT rescue with a documented $\sim 12\times$
wall-time penalty (per-chain Julia loop with PCIe round-trips).
v5's strong direct-Gaussian + 5-channel obs model does not need
OT rescue at the saturated config.

\paragraph{HARD chance-constraint deliberately out of scope.} Only
SOFT (Lagrangian-relaxed with constant $A_{\rm thr}$, default
0.05) is implemented. The HARD form (using
\texttt{find\_a\_sep}-derived per-bin $A_{\rm sep}$ as an
indicator) requires either CPU-side precompute of $A_{\rm sep}$
per (chain, bin) or a separate GPU prep kernel. Deferred.

\paragraph{\texttt{@match} site numbering.} v1.5 has 3 \texttt{@match}
sites (\texttt{paramsV15ToV1}, \texttt{reflect\_unit},
\texttt{apply\_prior}). v5 has zero --- no basis adapter (v5 uses
its own basis directly), no reflection (uses clamp/floor instead),
no separate prior transform exposed at the JSON layer. Don't look
for v5 \texttt{@match} sites.

\paragraph{If a phase gate fails.} Don't proceed to the next phase.
Almost every failure mode reduces to either (a) a wrong field
order in the JSON wire (Lean side) or the param Dict (Julia side),
or (b) an incorrect Lean $\to$ Julia idiom translation in the math
block. The diff test is precise about which function disagrees;
re-read the corresponding \texttt{Fsa/V5/<file>.lean} and the
Julia transcription side by side.
